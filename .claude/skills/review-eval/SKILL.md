# Review an evaluation run

The evaluation (`scripts/eval-models.mjs`, tasks in `shared/eval/tasks.json`) sends each task as the first message of a new conversation about a model store over `shared/fixtures/data/lecture.json`, through Mistral's API, and checks the store afterwards. This skill runs it, finds out why tasks failed and tries the smallest fixes. It never commits.

## Before running

- Build first: `bash scripts/build.sh`. The evaluation runs `build/client/`, so rebuild after every change you try.
- The FrameTrail working copy is `FRAMETRAIL_DIR` or `../frametrail`. Check that `node tests/run-js.mjs` passes; a failing test is fixed before anything is evaluated.
- The key is in `plans/a7-validation/.mistral-key`. Pass it as `--key-file=plans/a7-validation/.mistral-key`; never print it, never put it in a report.
- It is the maintainer's free Mistral plan: every run costs quota, and some models always answer 429 there. The model is `ministral-14b-latest` unless the user names another. Before a full run of more than one model, or with `--repeat` above 3, say how many tasks that is and ask.

## 1. Run

```bash
mkdir -p plans/eval
node scripts/eval-models.mjs --key-file=plans/a7-validation/.mistral-key --models=ministral-14b-latest --repeat=3 --json=plans/eval/<YYYY-MM-DD>.json
```

Add `-<n>` to the file name if one exists for the day. Each run in the JSON is `{ model, task, passed, failures, state, seconds, requests, rateLimited, invalid, tokens, tools: [{ name, state, input, error }], answer }`: the failed checks, every tool call with its input and error, and what the model said.

## 2. Find the cause of each failure

Read the failed runs: the task's request and checks in `shared/eval/tasks.json`, the tool calls in order, the answer. Compare with passing runs of the same task. Then pick one cause:

| Cause | Signs | Where a fix goes |
|---|---|---|
| Prompt text | It did not work the way the add-on wants: changed things for a question, did not read the transcript, guessed a ref, asked when it should have acted | `shared/prompts/system.md`, `conversation.md` |
| Operation description | Wrong tool, or right tool with input the description leaves open | `shared/operations.json`: the operation's or the input's `description` |
| Operation behaviour | Correct input, wrong result; an unclear error message the model could not act on | `client/ops/`, with a fixture case in `shared/fixtures/ops/` |
| Type knowledge | Wrong type, or a type's attributes used wrongly (wrong attribute name, value or meaning) | FrameTrail's schema descriptions (see below) |
| The task | The request is ambiguous, or the check rejects a right result | `shared/eval/tasks.json`, only with the user's agreement |
| Model limit | Fails at random across repeats with nothing to fix, rate limits, `invalid` calls the descriptions already rule out | nothing; note it |

What the model knows about types: the table in `shared/prompts/types.md` (the first sentence of each type's attribute-schema description in FrameTrail) and `describe_type`, which gives attribute names, types, values and defaults from `FrameTrailSchemas` but no descriptions. So a type-knowledge fix is a better first sentence of a type's description in FrameTrail, or a clearer name, value or default there; how to work with a type (where to place things, when to ask) is prompt text.

## 3. Try the smallest fix

- One cause at a time, the fewest words that address it. Show the user the change.
- Never edit `shared/prompts/types.md`: it is generated by `node scripts/sync-types.mjs` from FrameTrail's `docs/TYPES.md`. For a type-knowledge cause, write a note for FrameTrail instead: the schema file (`schemas/attributes/<type>.schema.json`), the description or property, and the wording you propose. It must not mention this add-on, models, AI, assistants, prompts or Mistral: it is a description of FrameTrail's data, for everyone who reads it. Do not change FrameTrail; the maintainer does.
- Rebuild, check `node tests/run-js.mjs` still passes, then rerun only the failing tasks with the same model and repeat count: `--task=<part of the task's name>`, one run per task, `--json=plans/eval/<YYYY-MM-DD>-<task>.json`.
- Compare with the first run. A fix that does not help is taken back. A prompt change can affect tasks that passed: offer a full run at the end, but ask first (quota).

## 4. Report

Write `plans/eval/<YYYY-MM-DD>-review.md`, short:

- the model, repeat count and score of the first run, and after the fixes;
- per failing task: the cause, the evidence (the tool calls or words that show it), the fix tried and whether it helped;
- the notes for FrameTrail's schema descriptions, worded as they would go there;
- what is left open.

Tell the user the scores and the open points, and leave every change uncommitted.
